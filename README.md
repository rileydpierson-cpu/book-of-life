# Book of Life

Book of Life is a server/app for browsing a personal journal and photo timeline.

## Architecture

- **Express server**: serves the UI, editor, auth, and timeline/media APIs.
- **Startup indexer**: recursively scans journal files, journal images, and photo folders.
- **Hidden cache**: stores the built index, photo-date metadata, HEIC conversions, and thumbnails in `.cache/`.
- **Frontend source**: Vite-powered vanilla JS in `client/`, built into `dist/`.
- **Filesystem source of truth**: journal entries stay as Markdown files on disk. The app index is a cache, not a second database.

## Frontend layout

- `index.html`, `editor.html`, `login.html` - Vite multi-page entry HTML files for `/`, `/edit/:date`, and `/login`
- `client/pages/` - page bootstraps and route-specific controllers
- `client/components/` - reusable UI modules such as the media viewer and modal controllers
- `client/domain/` - portable pure logic for calendar, time, folders, and timeline calculations
- `client/features/` - higher-level workflow controllers such as upload orchestration
- `client/core/` - shared utilities like API wrappers, script loading, and simple stores
- `client/styles/` - CSS entrypoints that compose the existing styling into page bundles
- `dist/` - built frontend output generated by `npm run build` and served by Express

The HTML entry files stay at the repo root on purpose. Vite treats root HTML files as first-class page entrypoints, so keeping them there makes multi-page routing and build output straightforward. They are still source files, but they function more like build entry manifests than ordinary components. They could be moved under `client/` later, but doing that would add path/config churn without much practical gain right now.

## Lazy-loading strategy

The app does **not** send the full timeline at once.

- The server keeps a sorted list of day entries in memory.
- The timeline API returns a **fixed slice of day blocks** by start index.
- The client loads only the requested chunk, centered on the chosen date when needed.
- As the user scrolls, top and bottom sentinels request **older** or **newer** day chunks.
- Jumping to a date uses the date rail index to fetch the chunk containing that day first, then scrolls to it.
- Search results reuse the same timeline renderer, but disable infinite loading so behavior stays predictable.

## Folder assumptions

Your folder configuration should point to:

- a **Journal Vault** folder that contains:
  - a `Journal` folder with files like `April 17, 2025.md`
  - an `Images` folder for journal inline images
- one or more **photo folders** that may be nested and messy

## Run locally

1. Copy `config.example.json` to `config.json`
2. Create a `.env` file in the project root
3. Add your folder paths:

```dotenv
LIFESERVER_JOURNAL_VAULT=D:\Notes\Journal Vault
LIFESERVER_PHOTO_ROOT=D:\Mission Photos
LIFESERVER_CACHE_DIR=./.cache
```

4. `config.json` can reference env vars with `${...}` placeholders, and the app will create these folders automatically if they do not exist
5. Optionally set `LIFESERVER_PHOTO_FOLDERS` for multiple photo roots. On Windows, separate folders with `;`, or use a JSON array string.

```dotenv
LIFESERVER_PHOTO_FOLDERS=D:\Mission Photos;D:\Family Photos
```

```dotenv
LIFESERVER_PHOTO_FOLDERS=["D:\\Mission Photos","D:\\Family Photos"]
```

6. Optionally enable auth and approve usernames in `.env`
7. In the project folder run:

```bash
npm install
npm start
```

Then open:

```text
http://127.0.0.1:3000
```

To use the app on your LAN, visit your machine's local IP on port `3000`.

Useful commands:

- `npm start` - build the frontend and then start Express
- `npm run build` - build the frontend only
- `npm test` - run Vitest unit tests for extracted frontend domain modules

## Authentication

If `auth.enabled` is `true`, Book of Life requires a username and password before loading the app.

Recommended config:

```json
"auth": {
  "enabled": true,
  "allowedUsers": "${LIFESERVER_ALLOWED_USERS}",
  "userStorePath": "./storage/auth/users.json",
  "sessionDays": 30,
  "secureCookie": false
}
```

Recommended `.env` values:

```dotenv
LIFESERVER_ALLOWED_USERS=alice,bob
```

Notes:

- `secureCookie` should stay `false` for plain local HTTP.
- If you publish this on the internet, put it behind **HTTPS** and set `secureCookie` to `true`.
- Users can sign up only if their username is explicitly listed in `LIFESERVER_ALLOWED_USERS`.
- Passwords are hashed and stored in the local JSON file at `auth.userStorePath`.
- Login sets an `httpOnly` session cookie.
- Environment variables in `.env` are loaded automatically at startup. Existing system env vars take precedence over `.env`.

## Entry editing

Book of Life now includes a Markdown editor for journal entries.

- Edit an existing entry using the edit button on a journal card.
- Use the calendar icon to jump to **today's entry**.
- If today's entry does not exist, the app creates the correctly named Markdown file automatically.
- Save using the top-right **Save** button or `Cmd/Ctrl + S`.
- Undo and redo are available with toolbar buttons and keyboard shortcuts.

Markdown files remain the source of truth. Saving writes directly to the correct journal file and refreshes that day in the in-memory index.

## Notes

- Journal dates come from the markdown filename only.
- Photo dates are determined in this order:
  1. manual date override saved by the app
  2. EXIF capture date
  3. filesystem created date
  4. filesystem modified date
- The upload dialog can stamp the selected day into the real image EXIF metadata instead of renaming files.
- If you have older photos whose dates only live in the filename, run `node scripts/apply-filename-date-overrides.js` to copy that date into EXIF on supported image types.
- `.heic` and `.heif` files are converted once and cached before browser delivery.
- Timeline thumbnails are cached at lower quality for speed.
- Full-size viewer loads the thumbnail first, then swaps to the full image.
- Background rebuilds run on an interval after startup.

## Developer map

### Runtime flow

1. `npm start` runs `vite build`, producing `dist/`.
2. `server.js` starts Express, auth, the indexer, and media services.
3. Express serves built HTML and asset files from `dist/`.
4. Each page bootstraps from its matching entry module in `client/pages/`.
5. Page controllers call shared domain logic, components, and API helpers.

### Where to change things

- Add or change API calls:
  Use `client/core/api.js` for frontend wrappers and `server.js` or `src/` for backend behavior.

- Add a reusable date/time/folder rule:
  Put the logic in `client/domain/` first, then call it from page or component code.

- Add a modal or reusable UI widget:
  Put the controller/component in `client/components/`.

- Add a page-specific interaction:
  Start in `client/pages/app/`, `client/pages/editor/`, or `client/pages/login/`.

- Add an upload workflow behavior shared by app and editor:
  Put the coordination logic in `client/features/upload/`.

- Change styling:
  Update the CSS entrypoint under `client/styles/`. Those files currently compose the existing app/editor/viewer styles.

### Current important files

- `server.js` - Express entrypoint, routing, and static asset serving
- `src/auth.js` - auth and login protection rules
- `src/indexer.js` - timeline indexing, search, and journal/media data loading

- `vite.config.js` - Vite multi-page build configuration
- `index.html`, `editor.html`, `login.html` - frontend build entry HTML
- `client/pages/app/main.js` - home/timeline page entry
- `client/pages/editor/main.js` - editor page entry
- `client/pages/login/main.js` - login page entry
- `client/components/viewer/create-media-viewer.js` - shared media viewer module
- `client/components/modals/` - reusable calendar, time picker, and folder picker modules
- `client/domain/` - portable frontend logic with Vitest coverage

### Mobile and hosting implications

- **Mobile web wrapper path**:
  The app can be wrapped in Capacitor or a similar container more cleanly because the frontend now has explicit build output and page entrypoints.

- **Native mobile path**:
  The extracted `client/domain/` logic is much easier to port or reuse while rebuilding the UI in React Native, Flutter, or another native stack.

- **Remote hosting path**:
  The built frontend in `dist/` can be served by the same Node process, behind a reverse proxy, or eventually split from the API layer if needed.

- **Testing path**:
  Pure logic in `client/domain/` can be extended with more unit tests without involving the browser UI.
